/little-flow · 核心功能与架构分析

Little Flow 轻量流程引擎

这是一个围绕 BPMN、MQ、Redis 上下文和业务节点注解构建的流程编排组件。它把流程图解析成可执行节点，通过消息驱动推进节点执行，并用 Redis 保存流程状态、上下文和锁。

核心功能 模块架构 运行架构 新建流程 节点执行 上下文与锁 类级职责 BPMN 细节 MQ 与重试 RocketMQ 专题 数据模型 代码索引 风险建议

核心功能

BPMN 路由

加载本地或远程 BPMN 文件，解析流程、子流程、网关和 ServiceTask，根据当前节点计算下一批可执行目标。

little-flow-camunda
消息驱动执行

把每个流程节点包装成 FlowNode，通过 Spring Event、ONS 或 RocketMQ 触发业务节点执行。

little-flow-mq
业务节点注册

业务类实现 FlowWork<String> 并标记 @LittleWorkFlow，启动后注册到静态 Map，消费时按 tag 分发。

little-flow-core
流程上下文

Redis 保存流程上下文、任务关系、重试信息和流程状态，支持按 key hash 分散到多个 Redis DB。

RedisFlowContextHolder
状态记录

节点进入 RUNNING、DONE、FAILED、ERROR 时发送流水记录，可通过 SPI 自定义展示内容和来源类型。

RecordService
回调与重试

支持异步回调后继续流程；抛出 RetryException 可重新入队，节点消费失败由 MQ reconsume 兜底。

状态流转

阶段 状态 主要动作
消息入队 未执行 生成 FlowNode，保存上下文，发送 topic/tag 消息。
节点开始 RUNNING 加节点锁，设置 stateMap[tag]=DOING，发送流水。
节点成功 DONE 合并 response 到上下文，保存上下文，触发后续节点。
节点失败 FAILED / ERROR 调用失败处理、错误通知，按异常类型决定是否重新入队。

类级职责拆解

从代码边界看，Little Flow 的核心并不是一个单体调度器，而是一组松耦合组件：BPMN 负责“找下一步”，MQ 负责“异步推进”，Core 负责“执行模板”，Redis 负责“把上下文留住”。下面是关键类的职责地图。

BPMN 解析与路由细节

加载阶段
  • BpmnLoader.afterPropertiesSet() 会在 Bean 初始化后尝试 reload()。
  • CommandLineRunner.run() 会再次兜底检查，加载失败时抛出 load bpmn files error。
  • lf.bpmn.loadType=local 时从 classpath 匹配 classpath:bpmn/new-process/*。
  • lf.bpmn.loadType=remote 时从 GSS bucket/folder/version 读取 BPMN。
  • 配置刷新时，如果 latestVersion 变化或 focusReload 开启，会异步重载。
解析产物
  • BpmnGroupPool 按版本保存 BpmnGroup。
  • processInfoMap 保存每个 BPMN process 的开始节点、属性、节点关系。
  • subProcessInfoMap 保存嵌套子流程元信息。
  • 节点属性来自 BPMN extension properties，例如 topic。
  • 网关输入输出关系用于并行网关汇聚和 latch。

路由策略

策略 对应 BPMN 元素 行为
StartEventStrategy startEvent 不是工作节点，通常直接进入后续节点。
ServiceTaskStrategy serviceTask 识别为真正业务节点，返回当前位置作为 NextTarget，由 MQ 触发执行。
ExclusiveGatewayStrategy exclusiveGateway 遍历 outgoing sequenceFlow，使用 FEEL 表达式匹配上下文，匹配失败时走 default 分支；没有 default 则抛异常。
ParallelGatewayStrategy parallelGateway 拆分出多个并发路径，汇聚时使用 SimpleSubTaskRecordLatch 记录所有输入是否完成。
SubProcessStrategy subProcess 进入子流程开始节点，或把子流程包装成新的 FlowNode 独立推进。
CallActivityStrategy callActivity 跨流程文件调用，依赖 call process id 查找另一个流程图。
EndEventStrategy endEvent 出栈并回到父流程或终止当前链路。

MQ、事件模式与重试机制

发送模式选择
  • lf.spring.event.enable=true：走 Spring ApplicationEventPublisher，适合单应用内快速验证。
  • lf.ons.enable=true：走 ONS sender，消费者由 ONS consumer 实现。
  • 默认路径：走 Apache RocketMQ sender/consumer。
  • 发送消息前会做上下文瘦身，避免大对象和 transient 字段进入消息体。
  • 消息 key 优先使用 flowId，否则使用上下文中的 FLOW_BIZ_KEY。
消费保护
  • 消费者启动 fast topic，存在 slow topic 时再启动 slow consumer。
  • 同一个 RocketMQ messageId 会用 Redis 加 3 秒短锁，降低重复消费窗口。
  • RocketMQ reconsumeTimes 大于 3 时直接消费成功并放弃执行。
  • 找不到 tag 对应的 FlowWork 时记录错误并消费成功。
  • 业务异常返回 RECONSUME_LATER，上下文丢失异常则消费成功。

重试分两层

层级 触发方式 行为 适合场景
业务节点主动重试 run() 抛 RetryException AbstractCommonFlowWork.exception() 从 ThreadContext 取原消息，扣减 retry 后重新 trigger.begin()。 业务明确知道可重试，例如外部服务短暂失败。
MQ 消费重试 process() 抛普通异常 RocketMQ listener 返回 RECONSUME_LATER，由 MQ 重投；超过 3 次后放弃。 无法区分原因或框架级异常。
发送失败重试 Producer 发送失败 RetryService 使用 Redis retry queue 保存待重发消息，按 lf.mq.retryFrequency 周期补偿。 MQ producer 短暂不可用。

RocketMQ 专题设计

在当前 Little Flow 中，RocketMQ 是默认的跨进程流程推进通道。它不保存流程上下文，Redis 才是流程状态的持久化位置； RocketMQ 负责把一个待执行的 FlowNode 可靠地投递到对应业务节点，并在节点完成后继续投递下一节点。 同一套生产能力还负责发送流程流水，但流水消息不进入 Little Flow 的业务节点消费链路。

1. RocketMQ 在系统中的位置

边界判断： FlowNode 的真实状态在 Redis；RocketMQ 中的消息只是“下一步执行意图”的传输载体。 因此消费端必须先恢复上下文，再按 stepId 和 stateMap 判断节点是否已经完成。

2. 消息模型：任务消息与流水消息

消息类型 Topic Tag Key Body 消费方
流程节点任务 FlowNode.topic，通常是 BPMN 节点 topic 或 fastTopic FlowNode.tag，对应 @LittleWorkFlow.value flowId，为空时回退到 FLOW_BIZ_KEY FlowNode JSON RocketMqWorkerListener
流程流水 lf.mq.flowTopic little-flow 媒资业务 key 或流程业务 key MediaFlowMessage JSON 流水/媒资平台消费者，不进入 Work 分发
失败节点路由 fastTopic processFailed 当前流程 key FlowNode JSON 失败处理 Work

Message {
    topic = flowNode.topic;
    tags  = flowNode.tag;
    keys  = flowNode.flowId != null
              ? flowNode.flowId

3. Producer 初始化与 AK/SK 热切换

  • RocketMqProducerRegister 固定 Producer Group 为 littleFlowProducerGroup。
  • AK/SK 通过 ConfigMapUtils 获取，凭证变化通过哈希值检测并重建 Producer。
  • Producer 使用 ACL Hook、NameServer 地址和 BizMsgQueueSelector，再套 Godeye CGLIB 代理。
  • 重建时先启动新实例，再将新实例放入 producer，最后关闭旧实例，避免凭证切换时完全没有发送者。

4. Topic、Consumer Group 与 fast/slow 双通道

通道 Topic 配置 Group 配置 线程配置 用途
Fast lf.mq.fastTopic lf.mq.fastGid fastMinThread / fastMaxThread 默认流程节点和高吞吐任务。
Slow lf.mq.slowTopic lf.mq.slowGid slowMinThread / slowMaxThread 耗时更长或需要独立隔离的任务。
Flow Record lf.mq.flowTopic 由流水消费者决定 生产端批量发送 节点状态、异常、业务流水上报。

fast/slow consumer 都订阅 * 标签，真正的业务分发由消息体中的 FlowNode.tag 完成。 这意味着 RocketMQ Tag 主要承担粗粒度过滤和通道隔离，业务 Bean 的精确路由由 flowWorkConcurrentMap.get(tag) 完成。

5. 消费时序与确认语义

条件 返回值 实际效果
业务 Work 返回 true CONSUME_SUCCESS Broker 删除/确认本次消息，流程后续节点由业务代码重新发送。
业务 Work 返回 false RECONSUME_LATER 交给 RocketMQ 消费重投机制。
普通异常 RECONSUME_LATER 由 Broker 重投，直到 reconsumeTimes > 3 后被确认放弃。
ContextLostException CONSUME_SUCCESS 当前实现选择不重试，避免上下文永久缺失时形成无效重投。
tag 找不到 Work、重复消息、超过重试次数 CONSUME_SUCCESS 消息被确认但业务不会再次执行，属于“记录错误并丢弃”策略。

6. 队列选择：按业务 tag 做流量分组

BizMsgQueueSelector 没有使用 RocketMQ 默认轮询，而是把物理队列按 queueNumRate 分成多个逻辑组。默认倍率为 5，目标是让不同媒资任务类型尽量落到不同队列组，减少某一种重任务把所有轻任务堵住。

Tag 关键字 逻辑队列组 设计意图
init组 0初始化类任务单独占用第一组。
meta组 1元信息任务分组。
snapshot组 2快照任务分组。
transcode / doc组 3转码、文档任务分组。
living / algo / download / complete / fail组 4直播、算法、下载、结束及失败任务分组。
其他 tag随机不参与固定分组，随机选择队列。
 
queueNum = brokerQueueCount
groupIndex = queueIndex % queueNumRate
queue = chooseGroupByTag(tag, groupIndex)

// 私有环境动态扩缩
desiredQueueNum = servicePodReplicas * minQueueRate

7. 三层可靠性策略

第一层：同步/异步发送

同步发送直接捕获异常；异步发送在 callback 的 onException 中进入 Redis 补偿队列。

第二层：RocketMQ 重投

消费者返回 RECONSUME_LATER，由 RocketMQ 重新投递；超过 3 次后当前代码确认放弃。

第三层：Redis 发送补偿

RdsRetryUtil 以 ZSET 保存到期任务，按 3s、5s、10s、15s、60s 递进重发。

8. Redis 发送失败补偿的内部结构

Redis Key 类型 内容 用途
{appId}_rocketMqRetryQueueLittleFlowtId:{taskId} String / binary 序列化后的 RetryTask<Message> 保存待重发消息实体。
{appId}_rocketMqRetryQueueLittleFlowtimeQueue ZSET member = taskId，score = expire timestamp 扫描已经到期的发送失败任务。
{appId}_rocketMqRetryQueueLittleFlowtLock:{taskId} 分布式锁 5 秒锁租约 多 Pod 竞争同一补偿任务时只允许一个实例执行。

9. 流程流水的批量发送

RecordService 不直接逐条同步发送，而是先把消息放入进程内队列；后台调度线程每秒取最多 50 条， 再按 recordBatchSize（默认 3）分片调用 sendMsgList。发送失败时，批次中的每条消息分别进入 Redis 补偿队列。 

messageQueue --(1s, max 50)-->
List<Message>
  --partition(recordBatchSize=3)-->
ApacheRocketMqSender.syncSendList()
  --failure-->
RetryService.addRetry(message)

10. 当前实现的关键风险

批量消费实际只处理第一条消息。

ApacheRocketConsumer.listen() 在 for (MessageExt msg : msgs) 循环中第一次迭代就直接 return callback.apply(msg)，因此 RocketMQ 批量拉取到多条消息时，剩余消息不会在本次回调中被处理。建议遍历全部消息，并按批次聚合确认策略重新设计。

多个“业务不可执行”场景会直接确认并丢弃。

超过重试次数、找不到 tag 对应 Work、重复消息抢不到 3 秒锁、上下文丢失都会返回 CONSUME_SUCCESS。这能避免无限重投，但必须有死信、告警或人工补偿，否则消息可能静默消失。

消费幂等锁不是业务幂等。

Redis 锁只按 consumerGroup + messageId 控制 3 秒内的并发重复消费，不能覆盖消息重发产生的新 messageId，也不能代替节点状态和业务唯一键校验。

队列分组依赖 tag 命名约定。

BizMsgQueueSelector 通过字符串 contains 匹配任务类型；新增 tag 若不更新映射，会落入随机队列，可能破坏任务隔离预期。

重试发送和原始发送的 topic 处理依赖对象可变状态。

sendMsg() 会把 topic 改写成 Wrapper topic，而 retryMsg() 不再做 wrapper。当前依赖同一个 Message 对象已被改写；若未来复制消息或改变失败时机，可能出现 topic 环境前缀不一致。

RocketMQ 设计结论： Little Flow 采用的是“消息驱动编排 + Redis 状态恢复 + 多层重试补偿”的模型。 RocketMQ 保证的是任务投递和重投，不保证业务节点 exactly-once；业务正确性最终依赖 stepId、stateMap、Redis 节点锁和业务侧幂等。

核心数据模型：FlowNode

FlowNode<Q, P> 是整个系统的运行时信封。它既承载业务数据，也承载流程图路由所需的栈、状态、后续节点和子流程信息。

字段 含义 生命周期
flowId 流程实例 id，主流程通常等于业务 key；子流程会生成 sub: 前缀 id。 创建流程时确定，贯穿上下文和消息 key。
parentFlowId 父流程 id，用于子流程回到父流程、并行网关汇聚。 创建子流程时设置。
stepId 当前 BPMN 节点 id，节点锁 key 和状态追踪会依赖它。 生成下一节点时由流程栈栈顶设置。
bpmnVersion / bpmnId 定位哪一版、哪一个 BPMN process。 新建流程或 routeFlow 时设置。
topic / tag MQ 路由信息。topic 可来自节点、子流程、流程级属性或 fastTopic 默认值；tag 对应业务 Work 名称。 每次生成下一节点时设置。
data 业务上下文 JSON，网关表达式、业务节点参数、流水扩展信息都从这里取。 流程创建时传入，节点执行成功后合并 response。
request / response 业务入参和返回值，标记为 transient，主要在本地执行期间使用。 消息发送和 Redis 存储时通常会瘦身。
next / prev 运行时链接节点，标记为 transient，避免序列化成巨大的链式对象。 路由下一批节点时临时构建。
nodeStack BPMN 双栈，保存 processId 栈和 flowNodeId 栈，用于递归走图、回父流程、routeFlow。 路由过程中持续 push/pop。
visitedFlowNodeIdSet 已访问节点集合，用于避免重复路径或辅助调试。 每次进入节点策略 before 阶段更新。
stateMap 按 tag 记录节点处理状态，例如 doing、finish、failed。 执行模板在节点开始和结束时更新。
subProcessFlow 记录子流程和父流程关系。 创建子流程时写入。
retry / timeout 节点重试次数和流程超时点。 进入流程或下一节点前由配置填充。

关键风险与建议

流程创建缺少空值保护。

BpmnFlowProcessor.createNewFlow() 在 BPMN 版本不存在或流程未加载时可能返回 null，NewFlowService.newFlow() 随后直接 stream()，会触发 NPE。建议返回空列表或抛出带 bpmnId/version 的业务异常。

Redis 上下文保存遇到 null 字段可能崩溃。

BizSerialization.encode() 对 null 返回 null，但调用处马上使用 tuple.get()。建议跳过 null 字段、显式保存 null 标记，或在进入上下文前做清洗。

Redis 健康检查永远为 true。

当前 fallback holder 基本不会触发。建议使用 PING 或轻量读写检查，并明确 Redis 不可用时是降级还是失败。

子流程属性向上查找疑似失效。

findProperties(SubProcessInfo...) 中 belongProcessId 和自身字段比较，条件恒 false。建议补充子流程继承 topic/配置的单测后修正。

消费者启动失败可能被日志吞掉。

buildConsumer() 捕获异常后只打日志，服务可能启动成功但没有消费能力。建议在关键 topic 配置存在时让启动失败显性化。

缺少测试保护。

当前未发现 src/test。建议优先补 BPMN 路由、Redis 上下文序列化、节点重试、并行/子流程 latch、MQ 消费分发五类单测。

一句话结论

Little Flow 的核心价值是把 BPMN 流程图转换成消息驱动的业务任务链。 它的扩展点清晰，适合多业务节点异步编排；目前最大的工程风险集中在异常可观测性、上下文健壮性和 BPMN 路由测试覆盖。
